# MTP pushes llama.cpp past 200 tok/s

llama.cpp on a single H200 can very likely hold about 200 tokens/second of single-stream decode for agentic coding with Qwen3.8-27B. It needs a Q4-to-Q6 GGUF, the model's built-in MTP head (`--spec-type draft-mtp --spec-draft-n-max 2-3`), one server slot, and a build from after the Qwen3.8 DeltaNet fix. No one has published a llama.cpp benchmark of this model on an H100 or H200. Every H200 figure below for llama.cpp is a projection from RTX 5090, RTX 3090 and H100 (Ollama) measurements, which scale closely with memory bandwidth. Without speculation, 200 tok/s is borderline: Q4_K_M projects to about 165-215 tok/s at short context and falls below 200 as context grows. With MTP, code-heavy output projects to roughly 250-350 tok/s, because MTP gains on code run highest (+90-150%). Above about 4 concurrent streams the picture reverses. MTP's benefit disappears, llama.cpp batches the hybrid DeltaNet layers poorly, and SGLang or vLLM deliver 2-4x more aggregate throughput. The only configuration measured above 200 tok/s per stream on an H200 is SGLang with the DFlash2 drafter, at 215-227 tok/s on code. The biggest practical obstacle is the tunnel, not the GPU. Cloudflare's docs say quick tunnels do not support Server-Sent Events, so streamed tokens can arrive in one burst, and any response silent for more than 125 seconds fails with error 524. A named Cloudflare Tunnel is needed to actually see 200 tok/s at the client.

## Qwen3.8-27B is a hybrid model, and that shapes every setting

Qwen3.8-27B (released August 2026) is "dense" only in that it is not a mixture-of-experts: all 27B parameters run for every token. It is not a full-attention transformer. Its 64 layers follow a repeating pattern of **three Gated DeltaNet (linear-attention) layers and one Gated Attention layer**. That makes **48 recurrent layers and only 16 layers with a growing KV cache** (4 KV heads, head dim 256). The model has 262,144 tokens of native context (YaRN extends it to 1M), a trained multi-token-prediction (MTP) head, and vision input ([Qwen/Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B)). In the unsloth GGUFs, the architecture string is `qwen35`, the native `qwen35.context_length` is 262144, and **the MTP/NextN tensors are already inside the main file** (`qwen35.nextn_predict_layers = 1`) ([unsloth GGUF header](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/resolve/main/Qwen3.8-27B-UD-Q4_K_M.gguf); [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp)).

The hybrid design has three consequences. First, the KV cache is small. From the card's dimensions, f16 KV works out to about 64 KiB per token, or about 16 GiB at 262K. That figure is arithmetic, not a measurement. On 141 GB, memory never forces the choice of quant or context. Second, decode slows little as context grows. On an H100, Qwen3.8-27B lost only **19% from 16K to 131K context (134 to 108 tok/s)**, while dense Llama 3.1 8B on the same card lost about half between 32K and 128K ([SimeonOnSecurity](https://simeononsecurity.com/articles/qwen38-27b-vast-ai-gpu-benchmark/)). Third, the recurrent DeltaNet state is hard to batch and hard to roll back. That is the root cause of llama.cpp's weak multi-slot scaling and of MTP's early limit to `n_parallel=1`.

Quant choice on an H200 is therefore purely about bandwidth and quality, because decode reads every weight once per token. The unsloth repo ([HF file listing](https://huggingface.co/api/models/unsloth/Qwen3.8-27B-GGUF/tree/main?recursive=true)) spans the sizes below. The projections assume 65-75% of the H200's 4.8 TB/s, the efficiency llama.cpp actually reaches on 27B models (about 69% on an RTX 5090, about 72-77% on an RTX 3090, about 68% for Ollama on H100).

| GGUF | Size | Bandwidth ceiling | Projected H200 decode, no spec | With MTP on code (projected) |
|---|---|---|---|---|
| UD-Q4_K_M / Q4_K_M | 16.5 GB | ~285 tok/s | ~185-215 | ~300+ |
| UD-Q4_K_XL | 17.6 GB | ~270 tok/s | ~175-205 | ~280-330 |
| UD-Q5_K_XL | 20.9 GB | ~230 tok/s | ~160-185 | ~240-300 |
| UD-Q6_K_XL | 25.3 GB | ~190 tok/s | ~140-160 | ~210-260 |
| Q8_0 | 29.1 GB | ~165 tok/s | ~105-120 | ~170-210 |
| BF16 | 54.7 GB | ~88 tok/s | ~56-65 | well under 200 |

The no-spec column comes from the throughput notes' projection. The MTP column applies the 1.5-1.8x gains measured on fast consumer cards and is the least certain number here. Two independent checks support the no-spec projection. Scaling H100 Ollama's measured 134 tok/s by the bandwidth ratio gives about 192 tok/s ([SimeonOnSecurity](https://simeononsecurity.com/articles/qwen38-27b-vast-ai-gpu-benchmark/)). The jump from RTX 5090 to H100 (1.81x) almost matches their bandwidth ratio (1.87x), which suggests little fixed per-token overhead at this model size. A note of caution: at 200 tok/s the whole budget is 5 ms per token. The H100 data limits fixed overhead to at most about 2.4 ms, and that overhead does not shrink on an H200. A realistic plain-decode range at Q4 is therefore **about 165-195 tok/s**, just short of the target.

## MTP supplies the headroom, but only for one stream

llama.cpp has supported the model's own MTP head since PR #22673, merged in May 2026. You enable it with `--spec-type draft-mtp`. The head runs as a separate small model loaded from the same GGUF ([PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)). Be careful with `--spec-default`: it turns on `ngram-mod`, not MTP ([common/arg.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp)). Measured gains on Qwen3.8-27B are large on fast cards. On an RTX 5090 with Q4_K_M, decode went from **73.6 to 133.6 tok/s at `--spec-draft-n-max 3`**, a 1.81x peak. Depths 2, 4 and 5 scored 125.5, 119.5 and 108.8 ([KGP Talkie](https://kgptalkie.com/tutorials/llm-benchmarking/qwen-3-8-27b-llama-cpp-speed-settings)). Another 5090 run with UD-Q4_K_XL reached 74.3 to 179.7 tok/s at n=4. On an RTX 4090, code specifically went from 44.7 to 114.7 tok/s (2.57x) while prose rose only to 59.5. A JSON/tool-call prompt hit **0.971 acceptance** ([sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp)). A controlled 25-prompt study on an RTX 3090 found n=2 best overall (+59.8%), with code gaining +92-99% at n=2-3 ([HackMD thc1006](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090)). Agentic coding output is mostly code, JSON tool calls and shell commands, which are exactly the high-acceptance cases. Even a conservative 1.5x on top of a 170 tok/s baseline clears 200.

The right draft depth on an H200 is probably **3**, possibly 4. Faster cards favor deeper drafts, and n-max 2 is the safe choice on slower ones. Tune it with a sweep rather than trusting a single number. Never use very deep drafts: depth 16 halved throughput on Strix Halo ([Context Studios](https://www.contextstudios.ai/blog/qwen-3-8-27b-hardware-guide)).

MTP has three costs. First, it helps one stream and hurts a crowd. On Qwen3.6-27B on a DGX Spark, MTP was **2.2x faster at concurrency 1 but slower at concurrency 4** (29.9 vs 41.5 tok/s), and it cut prompt processing from about 860-1,080 to 570-720 tok/s ([NVIDIA forum](https://forums.developer.nvidia.com/t/mtp-llama-cpp-a-look-at-qwen3-6-27b/370298)). Second, speculative output is not bit-identical to plain greedy decoding: 92-100% of requests had diverged by 1,600 tokens, for reasons not yet established ([HackMD thc1006](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090)). Third, the slower prompt processing matters for agents, which resend long prompts every turn.

Other speculation methods lose to MTP here. A separate 0.8B draft model was 29.8% slower than no speculation. Qwen3 0.6B/1.7B drafts use a 151,936-token vocabulary against Qwen3.8's 248,320 ([HackMD thc1006](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090); [Qwen card](https://huggingface.co/Qwen/Qwen3.8-27B)). llama.cpp's `draft-dflash` (DFlash2) roughly matched MTP overall on a 3090 (+51.9% at n=4) but beat it on code (+116.8%). It is worth a benchmark, though it needs an external drafter. `ngram-mod` helps only when output copies existing text, such as rewriting a file. Its acceptance swings from 0.92 to 0.00 on near-identical runs ([PR #19164](https://github.com/ggml-org/llama.cpp/pull/19164)). Stacking it as `--spec-type draft-mtp,ngram-mod` is syntactically allowed, but ngram compatibility was still a post-merge TODO on the MTP PR. Verify it on your build before relying on it.

## The recommended llama.cpp build and launch for one H200

Build for Hopper explicitly and leave the defaults alone. CUDA graphs and FlashAttention kernels are on by default. `90a` is pointless because ggml never emits it. `GGML_CUDA_F16` and `GGML_CUDA_PEER_MAX_BATCH_SIZE` no longer exist. `FORCE_MMQ`/`FORCE_CUBLAS` target prefill, not batch-1 decode ([ggml/CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/master/ggml/CMakeLists.txt); [docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)). Use a recent build. **Older CUDA builds produced garbage on Qwen3.8 through the DeltaNet path. The fix landed around b10450**, and all libggml/libllama libraries must be updated together ([discussion #27164](https://github.com/ggml-org/llama.cpp/discussions/27164)).

```bash
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=90-real -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j --target llama-server

./build/bin/llama-server -m Qwen3.8-27B-UD-Q4_K_XL.gguf \
  --host 127.0.0.1 --port 8080 --api-key "$KEY" \
  -ngl all -fa on -np 1 -c 131072 --fit off \
  -ctk q8_0 -ctv q8_0 -ub 2048 \
  --spec-type draft-mtp --spec-draft-n-max 3 \
  --no-mmproj --jinja --reasoning-format deepseek \
  --no-context-shift --cache-reuse 256 --metrics
```

Several choices in this command deserve explanation. `-np 1` maximizes per-stream speed and avoids the MTP concurrency penalty. Early MTP builds also refused `n_parallel > 1` ([PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)). `--fit off` with an explicit `-c` stops the default `--fit on` from silently picking a different context size. Set `--port` explicitly: the current README lists a default of 9931, not 8080 ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). For the KV cache, q8_0 is a sound default. On a 5090 with MTP at 32K, f16, q8_0 and q4_0 KV gave **125.5, 128.3 and 136.7 tok/s** respectively, with no reported quality loss ([KGP Talkie](https://kgptalkie.com/tutorials/llm-benchmarking/qwen-3-8-27b-llama-cpp-speed-settings)). q4_0 adds a few percent if you accept the risk. Matched K/V pairs (q8_0/q8_0, q4_0/q4_0) are already compiled into the default FA kernels. Mixed pairs need `GGML_CUDA_FA_QUANTS` ([docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)). `--no-mmproj` drops the vision encoder that coding does not need. Unsloth advises 1-2 GB of headroom for MTP, which is trivial on an H200 ([unsloth docs](https://unsloth.ai/docs/models/qwen3.8)).

**Do not enable YaRN.** Native 262,144 covers agentic coding, and the model card warns that static YaRN hurts short-text quality ([Qwen card](https://huggingface.co/Qwen/Qwen3.8-27B)). The bigger long-context risk is a bug. Open llama.cpp issue #27756 reports that **Qwen3.8-27B silently emits EOS as its first token once prompts exceed about 130K positions**, on both CUDA and CPU ([issue #27756](https://github.com/ggml-org/llama.cpp/issues/27756)). That is why the command caps `-c` at 131072. Raise it to 262144 only after testing long prompts on your build. Long prompts are also expensive. On a 5090, a filled 128K window took 78 seconds to first token ([KGP Talkie](https://kgptalkie.com/tutorials/llm-benchmarking/qwen-3-8-27b-llama-cpp-speed-settings)). An H200 will be faster but still takes seconds to tens of seconds at that size.

For sampling, Qwen's coding evaluations used the thinking preset (temp 1.0, top_p 0.95, top_k 20, min_p 0). Thinking runs at `reasoning_effort` `xhigh` by default. Unsloth shows how to lower it with `--chat-template-kwargs '{"reasoning_effort":"medium"}'` ([unsloth README](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/raw/main/README.md)). Lowering effort does not change decode tok/s. It cuts the number of tokens per turn, which often matters more for agent wall-clock time than raw speed. llama-server also serves `/v1/chat/completions`, `/v1/responses` and Anthropic-style `/v1/messages` with tool use ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). OpenAI-, Codex- and Claude-Code-style clients can all connect directly.

## A quick tunnel can erase the speed you just bought

The trycloudflare.com quick tunnel is the weakest link in the stack. Cloudflare states plainly that **"Quick Tunnels do not support Server-Sent Events (SSE)"**. Quick tunnels are also capped at 200 in-flight requests (429 beyond that), have no uptime guarantee, and get a new hostname on every start ([TryCloudflare docs](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/)). Every streaming OpenAI or Anthropic client uses SSE. A secondary report says the quick-tunnel edge buffers `text/event-stream` bodies, so tokens reach the client all at once when generation ends ([daleseo.com](https://daleseo.com/cloudflare-tunnel/)). The proxy read timeout is **125 seconds** (not the old 100), and only Enterprise plans can change it ([Connection limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/); [Error 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/)). If the stream is buffered, any turn that takes more than 125 s fails with a 524. At 200 tok/s, that limit is roughly 25,000 tokens of reasoning plus answer, which an `xhigh` thinking turn can exceed. The server is fast, but the client sees nothing until the turn completes.

The fix is a **named Cloudflare Tunnel**: a free account plus a domain gives a stable hostname and passes streaming through. That is Cloudflare's own recommendation for anything beyond testing ([TryCloudflare docs](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/)). If you must use a quick tunnel, do four things. First, run a `curl -N` streaming smoke test to see whether tokens arrive progressively. Second, bound `max_tokens` and `--reasoning-budget` so each turn finishes well under 125 s. Third, always set `--api-key`, because the URL is public. Fourth, re-read the URL from cloudflared's **stderr** after every restart, for example with `grep -oE 'https://[a-zA-Z0-9-]+\.trycloudflare\.com'`. Use `--protocol http2` if the GPU host blocks UDP/QUIC ([run parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/cloudflared-parameters/run-parameters/)). Reports conflict on whether quick tunnels really buffer every stream, and some users stream through them anecdotally. Treat the smoke test as the deciding evidence.

## SGLang wins the measured race and every crowded one

The only published single-H200 benchmark of this model is z-lab's SGLang run, and it sets a clear reference. Plain autoregressive decode at concurrency 1 ran at **69 tok/s**, consistent with BF16 weights at about 78% of the bandwidth roofline. Native MTP (7 draft tokens) reached **152-153 tok/s on HumanEval/MBPP**. **DFlash2 reached 215-227 tok/s on code**, with acceptance lengths of 4.39-4.79 against MTP's 3.91-3.99 ([z-lab/qwen3.8-27b-dflash2](https://huggingface.co/z-lab/qwen3.8-27b-dflash2)). The launch command is `python -m sglang.launch_server --model-path Qwen/Qwen3.8-27B --speculative-algorithm DFLASH --speculative-draft-model-path incoai/Qwen3.8-27B-DFlash2 --speculative-num-draft-tokens 8`. Add `--reasoning-parser qwen3 --tool-call-parser qwen3_coder` for agents ([z-lab card](https://huggingface.co/z-lab/qwen3.8-27b-dflash2); [Qwen3.6-27B card](https://huggingface.co/Qwen/Qwen3.6-27B)). These figures are BF16. An FP8 checkpoint should roughly double the plain-decode baseline and push MTP or DFlash2 well past 200, but no one has measured that. In vLLM, DFlash2 for Qwen3.8 still needs an unmerged PR build. Released vLLM offers native MTP via `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'` ([vLLM blog](https://vllm.ai/blog/2026-08-23-speculative-decoding-amd-gpus)).

Concurrency is where the engines diverge. On the H200, SGLang aggregates **1,090-1,368 tok/s at 8 concurrent requests with DFlash2 and up to about 1,950 at 32**. MTP turns into a net loss at 32 ([z-lab card](https://huggingface.co/z-lab/qwen3.8-27b-dflash2)). llama.cpp has no comparable Hopper data. On other hardware it scales poorly with this architecture. Batched decode of Qwen3.5-27B scaled only 2.75x at batch 32, versus 7x for dense Gemma 3 27B, because of non-matmul DeltaNet ops ([issue #20006](https://github.com/ggml-org/llama.cpp/issues/20006)). On identical consumer GPUs, vLLM beat llama.cpp **3.7x on aggregate chat and about 3.6x on agentic workloads at concurrency 64**, while the two tied at concurrency 1 (19 vs 20 tok/s) ([LLMKube](https://llmkube.com/blog/qwen3-6-27b-bakeoff)). The same bakeoff found vLLM's prefix caching cut agentic first-token latency to **409 ms versus 911 ms** for llama.cpp. That gap compounds over hundreds of agent turns. Prefix caching on this hybrid model is still young in both engines, though. vLLM's Mamba `align` mode is marked experimental, and SGLang needs `--mamba-radix-cache-strategy extra_buffer --page-size 64` ([vLLM APC docs](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html); [SGLang cookbook](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.5)). One llama.cpp correctness risk also argues against many slots: on HIP, recurrent state leaked between requests on a reused slot ([issue #29092](https://github.com/ggml-org/llama.cpp/issues/29092)).

The tradeoff is therefore clear. For one interactive agent, llama.cpp with a Q4/Q5 GGUF and MTP is the simplest way to about 200+ tok/s. A quantized GGUF reads about a third of BF16's bytes, which offsets SGLang's better kernels. It is also the only option of the three that uses the unsloth GGUF the question specifies. For several parallel agents or sub-agents, or when time-to-first-token on long, repeated prompts matters, SGLang is the better engine. Use DFlash2 at low concurrency and plain decode at high concurrency.

## Conclusion

The 200 tok/s target depends less on the GPU than on three choices around it. Speculative decoding is what turns a borderline bandwidth-bound baseline into comfortable headroom. Concurrency decides whether that headroom survives. The transport decides whether the client ever sees it. The H200's surplus memory (141 GB against a 17-25 GB model and a 16 GiB full-context KV cache) is mostly unused in a single-stream llama.cpp setup. That idle capacity is the strongest argument for SGLang when the agent workload grows beyond one stream. The key unknown is an actual H200 llama.cpp measurement. Before committing, run `llama-bench` and a `--spec-draft-n-max` sweep (2, 3, 4) on the target box with real agent transcripts. This one hour of testing replaces every projection in this report. Also check the >130K EOS bug and quick-tunnel streaming directly rather than assuming either works.
